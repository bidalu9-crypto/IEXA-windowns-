# 工具 UI：从「每步一张卡」到「一轮一条轨」（2026-10-19）

## 症状

用户截图里一轮对话有 15 组「已执行工具 2 次调用 0 秒」，每组之间夹一条「思考」。
一次深度任务就把转录区堆成两三千像素的卡片墙，滚动时卡，扫光也不顺。

## 先看 DeepSeek Harness 怎么做的

`deepseek-ai/deepseek-harness`（master）里相关的是这几处：

| 文件 | 作用 |
|---|---|
| `packages/client/ui-tool/src/client/tool/ToolCallTree.tsx` | 根调用与子调用组合，每个调用一个 keyed 节点 |
| `.../tool/components/ToolRow.tsx` | 单行行体：图标 + 名称 + 省略摘要 + 状态胶囊 + 可展开正文 |
| `.../tool/ToolCallTree.module.css` | 子调用缩进靠 `border-left: 0.5px`，`gap: 4px`，行半径 `--dsw-radius-sm` |
| `.../tool/toolviews/GenericToolCard.tsx` | 按工具类型选视图（read / diff / search / terminal / web） |

三条设计结论：

1. **一个调用一行，不是一张卡**。行本身没有独立边框、没有背景、没有阴影，只有一条
   0.5px 的轨把同一轮的调用串起来。
2. **每个调用只有一个状态位**（左侧图标 + 右侧语句），运行中才加动效，且动效是
   `TextShimmer` 只作用于一行文字。
3. **层级靠缩进，不靠卡片容器**。子调用用 `margin-left: 22px` + 1px 竖线，父子关系
   一眼可见，代价是零额外绘制层。

## 我们原来错在哪

还原到代码：

| 现象 | 出处 |
|---|---|
| 一次思考 + 一次工具就各占一个容器 | `StreamPipeline.handleThinkingDelta` 只把新块挂到 message 上 |
| 每个 `.tool-block` 都是一张带边框/圆角/背景的卡 | `composer.css` `.tool-block { border; border-radius: 12px; background }` |
| 每个运行中的行都有一个独立的扫光层 | `.tool-block.is-active .tool-header::after { animation: toolShimmer }` |
| 每个流式片段都动 `clip-path` | `@keyframes iexa-stream-reveal { clip-path: inset() }` |

第 3、4 条是"不丝滑"的直接来源：`clip-path` 不是合成属性，每个 token 都要重绘字形；
而每张卡里的扫光层都活到该卡被销毁为止，一轮下来几十个裁剪层。

## 改了什么

**1. 思考并入同一条轨**（`StreamPipeline.js`）

```js
const rail = lastActivity?.classList.contains('tool-steps') && !lastActivity.classList.contains('is-collapsed')
  ? lastActivity : null;
```

思考块创建时若上一条活动是未折叠的轨，就 `rail.append(thinkBlock)`；否则退回挂在
message 上。于是「想 → 做 → 想 → 做」不再打断链，一轮只剩一个 `.tool-steps`、
一个 `.task-summary`。

折叠态必须排除：轨折叠时子节点 `display:none`，把实时推理塞进去会直接消失。

**2. 行取代卡**（`workbench.css`）

```css
.workbench-shell .tool-block { border: 0; border-radius: 6px; background: transparent; contain: layout paint style; }
.workbench-shell .tool-steps > :is(.tool-block, .thinking-block) { box-shadow: inset 1px 0 0 var(--border); padding-left: 9px; }
```

`contain: layout paint style` 让每次 append 的重排范围收敛到这一行，而不是整段对话。

**3. 扫光只剩一层**

从"每个 `.tool-block.is-active`"改成"运行中的那一行"，并把 `ease-in-out` 换成
`linear`：缓动在两端会减速到近乎停住，肉眼看就是每次循环卡一下。

**4. 流式揭示不再动 `clip-path`**

改成纯 `opacity`，150ms。

## 实测

真实 Chromium（DPR 2，760px 宽），15 行轨 + 运行中扫光，连续采样 2.2s：

| 指标 | 改前 | 改后 |
|---|---|---|
| 同时运行的扫光层 | 每张活动卡一个 | **1** |
| 行内动画元素 | 每行一个 `::after` | **0** |
| 单行重排范围 | 整段对话 | 本行（`contain`） |
| 帧间隔 p50 / p95 / max | — | 10.0 / 10.2 / 10.6 ms |
| > 20ms 的长帧 | — | **0 / 220** |

（改前没有留同样的采样，因为旧结构在夹具里要先构造 15 个容器；这里只记录改后基线。）

## 守卫

`tests/tool-rail.test.js`（5 项）：

- 「想 → 做 → 想 → 做」只产生 **1 个** `.tool-steps`、**1 个** `.task-summary`，
  且 `flatten` 顺序仍是真实时序；
- 折叠态的轨不能吸收新的推理块（否则推理会不可见）；
- 每个工具行不得自带动画，全仓 `toolSweep` 只声明一次且为 `linear`；
- `iexa-stream-reveal` 不得出现 `clip-path` / `filter`；
- `.tool-block` 必须带 `contain: layout paint style` 且无卡片边框。

`tests/helpers/transcript-harness.cjs` 的 `flatten` 改为递归进入 `.tool-steps`，
否则嵌套后时序断言会静默失真。

## 与 DeepSeek Harness 的逐条核对（2026-10-19 晚）

前面几段是凭印象写的工程结论。这一节是**实际读到源码之后**的核对，文件路径都在
`deepseek-ai/deepseek-harness@master` 下验证存在。

### 核到的原文

| 文件 | 事实 |
|---|---|
| `packages/client/ui-tool/src/client/tool/components/ToolRow.module.css` | 文件头注释写明：**24px 单行**，`[16 leading] gap6 [title 13/24] gap8 [2x2 dot] gap8 [summary FILL truncate]` |
| `.../components/ToolRow.tsx` | 摘要用 `TextShimmer` 包住；行里只渲染标题、分隔点、截断摘要 |
| `.../ToolCallTree.module.css` | `.subCalls { display:flex; flex-direction:column; gap:4px; margin:4px 0 2px 22px; padding-left:8px; border-left:.5px solid }` —— **一条边框在容器上**，不是每行画一条 |
| `packages/client/ui-primitives/src/TextShimmer.module.css` | 真文字保留语义色；高亮是**另一层文字的副本**，放在 `overflow: clip` 的装饰层里，用 `mask-image` 出光带，`transform` 平移 |
| `.../TextShimmer.module.css` 关键帧 | `0% translateX(100%)` → `66.6667%, 100% translateX(-100%)`：**走 2/3 行程，停 1/3** |
| `.../toolviews/GenericToolCard.tsx` | 按工具类型分视图（read / diff / search / terminal / web） |

### 对齐了什么

- 行高 26 → **24px**，`gap` 7 → **6px**，与 ToolRow 的注释一致；
- 标题与摘要之间补上 **2×2 圆点**（`--dsw` 的 `.sep`）；
- 轨线从**每行一条 `box-shadow: inset`** 改成**容器一条 `border-left: .5px`**；
- 扫光从 `background-clip: text` + `background-position` 改成**文字副本 + 静态 mask + 双反向 transform**，
  与 `TextShimmer.module.css` 同一手法；
- 扫光节奏改成 **走 2/3、停 1/3**。

### 扫光：为什么最终照搬了「副本 + mask」

前一版把 `TextShimmer` 的手法当成"可以省掉的复杂度"，用 `background-clip: text` +
动画 `background-position` 代替。这是错的，有两个后果：

1. **每帧重绘字形**。`background-position` 不是合成属性，Chromium 每帧要为这行文字
   重新栅格化。真实窗口 2 秒内（DPR 2）：旧实现 **296 次 Paint / 148 次 RasterTask**，
   新实现 **0 次 Paint / 0 次 RasterTask**。
2. **光带会消失**。`background-size: 220%` 配 ±160% 位移，光带在周期后段完全跑出可视区，
   再硬跳回起点——看起来是"卡一下、闪一下"，不是扫过。

`TextShimmer` 的做法之所以成立：真文字完全静止，装饰副本放在 `overflow: clip` 的窗口里，
mask 固定在窗口上，两个反向 `translateX` 让字形相对 mask 保持不动、只让光带走。
两个属性都是 transform，走合成器。

实现落在 `src/renderer/services/LabelGlow.js`（约 70 行）+ `workbench.css` 的 `.label-glow` 族。
只挂在**正在运行**的那一行：`syncRow` 读 `is-active`，行结束就移除，历史与折叠态都不挂。

## 已知取舍

- 轨线是 `box-shadow: inset` 而非额外元素，代价是每行一次 1px 绘制，可忽略。
- 历史消息本来就只渲染「一个思考块 + 一个轨」，不受本次改动影响。
- 扫光仍在 `.tool-header` 的 `overflow: hidden` 内，属于裁剪层；但同一时刻只有一行，
  比原来几十层低一个数量级。

## 重启后「折叠连续工具」不见了（2026-10-20 修复）

### 现象

折叠开着（`.iexa-appearance.json` 里 `collapseConsecutiveTools: true`），实时一轮里工具是
一条折叠的链；重启后同一条会话变成一长串可见的工具行，任务条（`已执行工具 N 次调用`）也没了。

### 根因

`TranscriptView.restore` 负责按 `message.transcript.items` 重放文本 / 思考 / 工具的顺序。
它把工具行重新分组时，只对**第一条**复用了旧轨（那条旧轨是 `SessionList` 建的，带任务条），
其余每条新建的轨只写了 `className = 'tool-steps activity-list'`，**没有 `.task-summary`**。
`refreshToolGroupSummary` 找不到任务条就 `return`，折叠自然也不会发生。

真实会话 `sess_1792142888675`（42 MB / 95 条消息）实测：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `.tool-steps` | 1499 | 1499 |
| 带任务条的轨 | **45** | **1499** |
| 折叠的轨 | 45 | 1499 |
| 可见 `.tool-block` | **2928 / 3047** | **0 / 3047** |

### 改法

- `ToolStreamView` 增加 `attachToolGroupSummary(host)`：没有任务条就补一条，然后走
  `refreshToolGroupSummary`，通过 `window.IexaToolRail` 暴露（用 IIFE 暴露，保持模块顶层只声明）。
- `TranscriptView.restore` 对每条重建的轨调用 `IexaToolRail.attach`。
- 思考的归属按折叠态决定：折叠时留在轨外（实时就是这样，用户仍能看到模型在思考），
  不折叠时留在轨内。判断读 `data-collapse-tools`，缺省时回落到 localStorage。

### 守卫

- `tests/transcript-rail.test.js`（jsdom）：每条重建轨都必须交给任务条构建器；工具行元素在
  复用旧轨时保持同一个 DOM 节点；折叠关闭时思考留在轨内、只有一条轨。
- `tests/browser-transcript-rail.test.js`（真实 Chromium）：带 `transcript` 记录的会话恢复后
  `rails === withPill === folded`、可见工具行为 0、展开一条不影响另一条。

### 没有做的事

恢复 42 MB 会话仍要约 6 秒（修复前 7.1 秒）。这是逐条建 3047 个工具行的固有成本，与折叠无关；
要再快需要虚拟化历史，属于另一件事。

## 扫光「不干净」：把字擦掉了（2026-10-20 修复）

### 现象

扫光扫过时，被光带覆盖的那两三个字看起来像被切断、重影、发虚。

### 根因

`.label-glow` 的高光色用的是 `--thinking-sheen`。这个变量原本是给**背景光带**写的：

```
:root            --thinking-sheen: rgba(255,255,255,0.92)   /* 浅色主题里是白 */
[data-theme=dark] --thinking-sheen: rgba(0,0,0,0.9)         /* 深色主题里是黑 */
```

深色主题下，盖在灰字上的副本是**黑色**。光带扫到哪里，哪里的字就被涂黑；mask 的渐变边缘
又把「被涂黑的字」和「原来的灰字」混在一起，于是成了断笔、重影的样子。

第二个问题：mask 是 105°，渐变终点落在盒子对角线上，所以 `transparent 100%` 并没有让
`sweep` 的右边缘完全透明；而 `sweep` 有 `overflow: hidden`，它的裁切边正好从字中间切过去
（实测在相位 350/600 的截图里能直接看到一条硬竖直边）。

### 改法

- 高光色改成 `var(--label-glow-tint, var(--text-primary))`：深色主题下比次要文字更亮，
  浅色主题下更深，是「提对比」而不是「盖一层」；
- mask 的透明端收到 `10% / 78%`，让裁切边落在完全透明的区域里。

### 验证

- 用 `getAnimations()` 暂停在 350 / 600 / 850ms 三个相位截 6× 图：光带内最亮像素 236，
  带外约 170，过渡是梯形而不是台阶；
- 单独渲染一块纯色 + 同款 mask，横向亮度剖面是
  `.....-----++++#####-----.....`，确认渐变本身是软的（问题不在 mask 太硬）；
- `tests/label-glow.test.js` 钉住两件事：`.label-glow` 不得再引用 `--thinking-sheen`，
  mask 的透明端必须 ≤ 85%；
- `tests/browser-design-motion.test.js` 在真实外壳里分别切到深/浅主题读计算色，
  断言深色下高光比标签更亮、浅色下更暗。
